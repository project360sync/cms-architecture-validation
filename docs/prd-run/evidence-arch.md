[ARCH §0] Thesis: two cleanly separated layers — STRUCTURE (developer-owned annotated HTML/CSS + locked versioned GSAP JS bundle) and CONTENT (client-owned named, typed fields + collections); render merges them and JS runs on the rendered structure.
[ARCH §0] Content is bound to a NAME, not an HTML position, so restructuring the template does not destroy client content.
[ARCH §0] The model is essentially Shopify Online Store 2.0's sections model, but applied to arbitrary annotated HTML (not a templating language) and preserving bespoke author JS.
[ARCH §0] Document is a greenfield concept for validation before final implementation; status proposal, dated 2026-07.
[ARCH §1] Core problem: make an animated, JS-driven (e.g. GSAP) bespoke page editable by a non-technical client without letting them break it.
[ARCH §1] The current already-partly-built model uses position-based data-cms-id annotation with overrides on a stored skeleton; works but fragile (document-order ids drift on reorder, edits orphaned).
[ARCH §1] Prior art Instatic: one-way HTML import into own node tree, store becomes truth, discards <script>.
[ARCH §1] Prior art Shopify OS 2.0: Liquid + {% schema %} + JSON template; strong prior art for name-keyed robustness but doesn't prove annotated-HTML import, auto migration, or bespoke-JS lifecycle.
[ARCH §2] Goals: content ⟂ structure separation; developer owns structure in code, client edits only content within permitted bounds; GSAP survives on published page; per-module editability with palette; robustness to structure updates; framework-agnosticism (annotate arbitrary static HTML).
[ARCH §2] Non-goals: templating language; general drag-drop page builder; client-side structure editing beyond palette boundaries.
[ARCH §3.2] Annotation convention: default everything locked, only marked parts editable; stable section-instance ids never generated from document position; multiple instances per type possible; collections via <template data-cms-item> prototype.
[ARCH §3.4] Per-section-type schema (fields, types, labels, defaults, validation) drives editor UI + validation; initial field types: text, longtext, richtext, image, url, select, color, number, boolean.
[ARCH §3.4.1] Permission ≤ capability, enforced at manifest compile; fixed mode forces composition permissions false; three independent locks (content/position/structure).
[ARCH §4.1] Onboarding import is one-time (not continuous overlay); thereafter content store is truth.
[ARCH §4.2] Two render modes (fixed / composable) decided by template manifest; typed renderer encodes+validates by context on EVERY write.
[ARCH §4.3] Publish = immutable static snapshot exported to edge (client's own domain); editor CMS scale-to-zero, not in visitor path.
[ARCH §4.4] Re-ingest reconciles by name not position; disappeared slots quarantined, not silently dropped; versioned migration manifest for schema changes; transactional preview + rollback.
[ARCH §5] Granular editor permissions from manifest, server-side enforced; hybrid editor (inline click-to-edit + settings panel); AI-chat issues same typed ops, Guardian-validated, client never supplies markup; Edit AND Preview sandboxed on separate origin.
[ARCH §6] Author JS = locked, versioned, content-addressed bundle, part of the template; content-edit doesn't change animation because content is a value in fixed DOM; section add/reorder disabled by default on bespoke pages (GSAP break risk).
[ARCH §7] Storage: content typed/schema'd/versioned; Mongo works now, Postgres+JSONB cleaner for typed content; model store-agnostic.
[ARCH §8] Name+type model survives source reorder, separates content/structure, makes redesign safe, addItem trivial, schema change a flagged migration; current impl's bugs stem from position anchoring.
[ARCH §12.1] Sweet spot / ICP: bespoke, art-directed, largely static brand/marketing site (agency-built, GSAP, custom design) maintained by non-technical client at copy/image/repeating-card level while developer owns structure — real, underserved, NARROW niche.
[ARCH §12.2] NOT-for: transactions/real-time (→Shopify/headless commerce); content graph w/ reused entries (→headless CMS Sanity/Contentful/Storyblok); many data-generated pages (→Astro/Next+source); dev-less DIY (→Webflow/Framer/Wix/Squarespace); client design freedom (→Webflow/Framer or Shopify theme editor); enterprise localization workflow (→enterprise headless); app-level interactivity (→app-blocks/integrations/embeds).
[ARCH §12.3] Sharpest internal limit: GSAP × content-reflow — longer text / more items / different aspect ratio can break hand-tuned pin/measured-distance/SplitText animation; the more bespoke the animation, the less safe free content-edit; mitigation (§14.5) reduces but does not eliminate.
[ARCH §12.4] When user better served otherwise: shop/booking→Shopify; content-heavy→headless+SSG; self-build→Webflow/Framer; frequent structural change→builder; multi-language enterprise ops→enterprise headless; rare edits (few/yr)→don't build a CMS at all (tiny form or do-it-for-them).
[ARCH §12.5] Demand risk (most important non-technical validation): seemingly-fitting clients slip into adjacent categories with strong incumbents. Exact question: "How many real clients = bespoke-animated page + wants copy/image-level edit + developer stays in loop — AND no adjacent solution serves them better?" Validate BEFORE writing code.
[ARCH §13] Success criteria: content survives dev restructuring+re-ingest (no id-drift/silent loss); client edits only permitted things, can't wreck design; GSAP runs on published page, content-edit doesn't break animation; addItem/field-edit simple data ops; framework-agnostic.
[ARCH §14] i18n = locale dimension on content layer; structure single-source; per-field translated/untranslated/stale states; publish policy required/fallbackAllowed/hiddenWhenMissing; AI translation is a headline feature (translates data, never markup).
[ARCH §14.5] Reflow-safe animation mitigation: animate length-tolerant sections, few; wrapper not text node; runtime measure + refresh; maxLength hints; mandatory locale × viewport × font visual/overflow test before publish; reflowSafe is a developer promise, not auto-derivable.
[ARCH §15] Review verdict: conditionally valid — good base for narrow §12.1 market; implementation only after applicable P0 gates.
[ARCH §15.1] P0 gates: fixed-vs-composable render contract; canonical identity+schema; secure render contract; migration protocol; draft/publish consistency; runtime isolation+lifecycle; locale publish-policy. Applicable-per-capability, not all before spike.
[ARCH §15.2] P1 (before pilot): asset lifecycle, conditions without templating language, capacity limits, fail-closed validation order, ops (quotas/observability/backup), roles developer/editor/publisher with AI on same permission layer.
[ARCH §15.3] Three phases: (A) v1 minimal spike = fixed-only, single-editor, single-locale (identity+manifest, typed render on every write, minimal rename/quarantine migration + revision + rollback, fixed GSAP lifecycle under longer text, item add/reorder without section move, atomic publish, mixed lock-policy). Go condition: no content loss, no active injection, atomic/rollbackable publish, deterministic animation re-init with longer text. (B) Before production pilot: optimistic concurrency, full locale-policy, audit/RBAC, asset lifecycle+ops. (C) Phase 2: composable (registry, add/remove/reorder, capabilities+tests, per-locale order).
[ARCH §15.3] No-go/pivot: if core thesis needs general template-runtime or content graph → headless CMS + SSG likely cheaper and better serves the user.
[ARCH §15.5] Ten §11 questions resolved: manifest mandatory; explicit migration map; one content schema two template modes; bespoke GSAP defaults fixed; production baseline Postgres+object storage (spike may stay Mongo); inline for quick edits + panel for canonical form; agnostic at build-output not source-framework; media by immutable asset-id; template import privileged, content-edit not code; revision-based draft + atomic release pointer.
[ARCH §15.6] Dual go/no-go: Architecture go (spike tests pass) AND Product go. Product-go bar (quote): "in real agency/client discovery multiple concrete projects show that annotated existing build + narrow client-safe edit + bespoke JS together are a PAID need, and the team can document why Webflow/Framer or headless CMS+SSG is not enough for that project; interest or generic 'would be nice' is not enough — pilot commitment and real templates required."
[ARCH §15.6] If only one gate passes: no full platform build. Technical failure → pivot headless/SSG integration; demand failure → spike stays internal agency tool or stops.
[ARCH §15.7] Resolved v1 decisions: pessimistic page-level edit-lock (heartbeat ~30s, TTL 2–5min, admin force-unlock, re-entrant per user incl. AI-as-user; others read-only); Edit AND Preview sandboxed separate-origin; v1 = fixed-only; spike may stay on Mongo as logic prototype.
[ARCH §16.1] Canonical content schema resolved: field identity = (scopeId, fieldName), never type-keyed; blocks get stable ids; structure locale-independent, only values locale-scoped; content.schema.json with referential integrity must land before spike.
[ARCH §16.2] Full migration protocol: explicit manifest wins over auto name-match; name-swap can't silently corrupt; cross-section move explicit; item-schema change draft-quarantines instead of fail-closing site; operators rename/move/transform/split/merge/delete with rollback; mandatory dry-run diff with human approval.
[ARCH §16.3] Full sink list (text/richtext/url/image/color/select/svg with per-sink policy; CSS-as-content explicit sink); import isolation (SSRF egress-allowlist, unpack limits, credential-less build, dependency provenance); full published CSP (default-src 'none', connect-src allowlist, nosniff) + postMessage origin/schema validation + separate registrable domain.
[ARCH §16.4] v1 revision-guard: every write carries base revision, stale writes rejected; AI writes to review-staging with bulk confirmation + rate limits; force-unlock fencing token.
[ARCH §16.5] Store wording: first PRODUCTION impl = Postgres + object storage; Mongo spike = logic prototype behind repository interface; green Mongo spike does NOT validate production store atomicity.
[ARCH §16.6] Sequencing reversed: demand gate BEFORE technical spike. Concierge design: deliver client-safe editing to 2-3 real HU clients using ONLY existing tools (Storyblok Visual Editor or edit-N-fields form on a bespoke build) at real price; measure instrumentally: (a) buy at price, (b) actually edit + frequency, (c) off-the-shelf demonstrably failed on GSAP, (d) stay vs slip to Shopify/Webflow/nothing. Go-threshold: "≥N committed paying clients where an off-the-shelf editor demonstrably failed on the bespoke motion" (N unset in doc — resolved by decision register D1). Then narrowed spike: GSAP mount/refresh/destroy survives typed edit + longer text on a real reference page across locale × viewport × font — WITHOUT front-loading migration engine / atomic publish / security-render pipeline.
[ARCH §16.6] Value-prop honesty: §14.5 mitigation narrows the differentiator (safe animation set overlaps Webflow/Framer native); remaining unique value = preserving bespoke motion on an existing hand-built page + developer-owned structure — gate 1 must PROVE it, not assume.
[ARCH §16.7] Readiness after round 2: schema codeable, reconciliation specified, security enough for spike, v1 concurrency closed, sequencing reversed; remaining condition is STRATEGIC (demand gate first).
